## Encrypted installation backup and recovery

`bonafides.installation_backup.capture_installation` now takes a matched native PostgreSQL 18 custom-format dump and referenced immutable blobs under the existing quiescent controller. The runtime role exports only the product schema, not the private migration ledger. A shared migration lock and exported PostgreSQL snapshot bind the dump, table-content fingerprints, references and configuration/key identities to one cut. PostgreSQL bytes are streamed through public-recipient encryption before staging; blob bytes stream into the outer encrypted archive. The detailed manifest is encrypted. Format v1 uses OpenSSL CMS AuthEnvelopedData with streaming BER, AES-256-GCM and RSA-OAEP-SHA256 recipients of at least 3072 bits. Bounds are 4 GiB ciphertext, 2 GiB plaintext dump, 16 MiB manifest and 100,000 data members plus the manifest. Hitting a bound fails rather than truncating or falling back to plaintext.

`bonafides.backup_archive.recover_bundle` requires an independently trusted ciphertext digest and a separately supplied private key. It copies untrusted ciphertext into private quarantine, verifies the digest and authenticates the complete outer envelope before parsing any tar data. Only exact declared regular members, hashes, sizes, paths and zero end padding are accepted. Both envelopes must use the supported authenticated format; ordinary unauthenticated CMS envelopes are rejected. Decrypted bytes remain in the offline private context and are removed on exit.

`bonafides.installation_restore.restore_installation` requires a separate migrator connection, an empty PostgreSQL/blob target, matching reviewed migration sources and compatible credential-key escrow. It validates native table/relationship fingerprints and the complete blob set before invalidating restored authority. A fresh installation namespace is bound to authenticated credential envelopes without reconnecting providers; sessions, approvals, OAuth transactions and pending work are revoked or cancelled, sources and hosted mode stay disabled, and maintenance stays closed. The private Alembic ledger is initialized with the standard stamp operation only after the exact public migration identities are verified. No target is automatically promoted.

Disabling an active source during native recovery advances both its object and policy versions and clears its current review pointer and review timestamp. Immutable policy-review history and linked postings remain intact. The source identity trigger and deferred review foreign key remain enforced; recovery does not bypass them.

Private SQL quarantine also requires the database-scoped `TEMPORARY` privilege. Fresh production initialization grants it to `bonafides_runtime`, without granting persistent-schema `CREATE`, and gives the migrator only the corresponding temporary-privilege grant option in addition to its existing schema-migration authority. This matters when PostgreSQL, rather than the migrator, owns the database: the frozen migration's `GRANT` otherwise emits a warning without granting the capability. A product-schema-only native dump does not contain database ACLs, so native recovery restores and verifies this minimum runtime privilege before invalidating authority. A runtime-role regression actually validates a nonempty archive in temporary quarantine and compares every native table fingerprint before and after; removing the recovery grant makes it fail.

### Daily scheduling, copies and retention

To enable startup catchup and the lifecycle worker's 60-second due check, add `schedule` to the same protected capture JSON and mount that configuration, its public recipient and the destination directories into the lifecycle service. ## Reviewed résumé import contract

The saved-import UI accepts a PDF/plaintext file or pasted text, lists prior batches and displays inert extracted text, exact quotes, source hashes and editable structured profile entries. Extraction and entry projection are deterministic and local, not AI or credential verification. Explicit skill separators produce individual skills; bounded literal headings, date ranges and continuations group work, education and projects. Ambiguous categories remain Needs placement rather than becoming miscellaneous facts automatically. Wording and repeated occurrences are preserved, recognizable contact/reference details excluded, and dates/metrics are not invented. No OCR, model/provider call, hosted extraction or alternate extraction engine is available.

Literal `MM/YYYY` date ranges normalize to `YYYY-MM` without adding precision. Solid-circle bullets are supported alongside ordinary bullets; a dated job groups its own continuations without absorbing the next job. Named bullet projects and separate pipe-delimited qualifications remain separate entries. Explicit technical-proficiency headings and bulleted category labels support comma-separated individual skills, preserving multiword names and intrinsic slashes such as `C/C++`. Project subheadings before named bullet entries and explicit notes sections require placement instead of becoming project facts automatically.

For selectable PDFs, bounded position/font-aware reconstruction reunites glyph fragments into physical lines and joins only geometrically clear wrap continuations. Short lines, bullets, headings, separated columns and page boundaries remain distinct; no characters may be lost, duplicated or reordered. Only whitespace is reconstructed, and every proposal still quotes an exact Unicode span in that normalized source. Unsupported or ambiguous layouts retain the original plain extraction order with `pdf_layout_requires_review`, rather than silently rearranging text. Optional font-metric construction, mapping, width or name failures also discard the entire page's reconstruction and preserve its complete plain extraction order; resource-limit, memory and recursion failures still refuse the import. The pinned pypdf font-metric API supplies glyph advances; reconstruction never allocates padding proportional to coordinates. Plaintext normalization, the 100-proposal cap, all parser resource limits and explicit review-before-merge remain unchanged.

All paths below are relative to `/api/v1`, owner-scoped and protected by the existing same-origin session/CSRF boundary:

| Operation | Request/result |
|---|---|
| `POST /imports` | Raw bytes, `Content-Type: application/pdf` or `text/plain` (optional UTF-8 charset), `X-CSRF-Token`, quoted **profile** `If-Match` and `Idempotency-Key`; returns 202 `{import_id, workflow_id}`. No multipart/filename/path input. |
| `GET /imports`, `GET /imports/{id}` | Bounded saved-batch list `{items: [...]}` or batch detail with workflow state/version, media/byte size/time, source digest/text, `entries`/warnings, captured `profile_version`, current `comparison_profile_version` and safe error code. |
| `POST /imports/{id}/merge` | Quoted current **profile** `If-Match`, `Idempotency-Key` and `{mode: "merge" \| "replace_all", replace_all_confirmed, decisions: [{source_ids: [UUID, ...], action: "skip" \| "add" \| "replace" \| "unchanged", claim_id?, kind, identity_field?, payload}]}`; returns 202 `{import_id, workflow_id}` and resumes the same workflow. |

The durable `profile_import` workflow stores original bytes privately and stages normalized text/raw literal fragments in `waiting_for_approval`, releasing its execution lease without writing canonical profile/evidence/claims. Staged fragments remain immutable, including for existing saved batches. Batch reads project `entries` containing `entry_id`, nullable `kind`, optional `identity_field`, evidence-linked profiles typed `payload`, `issues`, `sources: [{source_id, start, end, quote}]` and `comparison: {status, target_claim_id, candidate_claim_ids}`. Source IDs are deterministic; offsets and quotes identify exact Unicode spans, including distinct repeated occurrences. Projection does not reparse the upload, rewrite staged JSON or advance the workflow/profile version. Review expires independently after seven days; resumed execution is bounded to 60 seconds.

The default review is a complete, sectioned profile preview, including unrelated saved facts retained by ordinary merge. Skills and languages use compact editable chips, not a mandatory entry queue. Clean new entries are included in the unsaved preview and exact uniquely matched entries are marked unchanged without individual Keep clicks. Editing updates the preview; only conflicts, uncertain extraction, invalid values and ambiguous placement need individual correction, confirmation or exclusion. One final approval covers the assembled profile, not a claim that every entry was separately reviewed. Nothing is published before explicit batch approval.

Comparisons are server-derived against the current profile version. Status is `new`, `unchanged`, `conflict` or `needs_attention`. Matching is exact and same-kind: multiple equal saved candidates remain ambiguous. Changed experience/education candidates require identical nonempty organization, role and start date; project candidates require an identical nonempty URL; other categories use exact text. Similar wording or a different job start date does not establish identity. Replacements retain current preview fields until a choice is made; missing incoming fields preserve populated current values unless explicitly cleared.

Decisions partition all projected source IDs exactly once, allowing user grouping/splitting without client-authored provenance. Unplaced accepted entries, missing/duplicate/foreign source IDs, duplicate mutation targets, archived/foreign/wrong-kind replacements and over-capacity batches are refused. Repeated read-only `unchanged` decisions may share one uniquely matched claim, but mixed replacement/unchanged references may not. Personal details compare canonical current values and update only `display_name` or `headline`, at most once per field; identical values need no overwrite confirmation. Payloads retain evidence-linked profiles field/date rules. A 412 or stale comparison requires explicit comparison/rebase while retaining buffered edits, never silent overwrite. Pending merge blocks conflicting local editors; dirty buffers guard sign-out/navigation and remain available on network/session failures.

Worker publication rechecks the exact approved profile version, targets, quotas, expiry, cancellation and installation/workflow fences under the commit lock. Failure leaves no partial canonical mutation. Changed batches create one profile revision, immutable imported-source evidence and added/replaced non-identity claim revisions; personal details update the canonical snapshot instead of creating identity claims. An all-unchanged ordinary merge completes against the existing profile revision without new claims, evidence or profile revisions, while retaining the uploaded artifact and import audit. The server validates unchanged payloads and unique active targets rather than trusting the client flag. Explicit equal-value replacement remains available to attach this upload's source evidence.

Evidence contains the original normalized source digest and server-built exact source parts, never edited replacement text masquerading as a source quote. Support remains `user_asserted`, not independent verification. Ordinary merge preserves unrelated facts/sources and untouched identity/contact fields. Separately confirmed `replace_all` archives displaced active claims/sources while preserving unchanged targets, their evidence, identity provenance and immutable history; accepted personal details still update their explicitly chosen fields. It is not erasure. Idempotent replay cannot duplicate the merge.

The dedicated parser service has no network, secrets, DB or blob mount, a read-only root and a private import spool; both PDF and plaintext run in a supervised sealed child, never in API/worker. Limits are 10 MiB upload, 50 PDF pages, 2 MiB decoded content per page/16 MiB total, 80,000 Unicode scalars and 256 KiB normalized UTF-8 output, at most 100 proposals and a 30-second parser timeout, plus CPU/memory/file/process limits and process-group kill/reap. Strict UTF-8, CRLF/CR-to-LF and NFC normalization preserve remaining whitespace. Broken/encrypted/image-only/empty/over-limit inputs fail visibly, never as successful empty fallback. Source text stays out of audit/outbox/errors/logs; embedded instructions remain data.

Structured projection permits at most 1,000 source parts/review decisions while retaining the parser's 100-raw-fragment cap. The worker validates this projection before staging any parsed text or review data; an over-limit source stops with `import_source_limit` and readable failed-batch details instead of an unreviewable staged batch. An accepted entry's combined original evidence cannot exceed 4,000 characters; the existing active-profile limits remain 100 claims and 200 evidence records. A complete preview can exceed those storage quotas; displaying 106 entries does not mean 106 new claims can be saved. This change removes redundant review steps, not storage limits.

Manual entry and imports share `ClaimKind`/`ClaimPayload` and the saved profile/evidence revision model. Current import provenance supports normalized text spans only; no LinkedIn/Naukri structured-export adapter, direct account sync or general provider-connector framework is implemented. Future structured adapters must map into the shared draft/review boundary and supply truthful row/column or JSON-path provenance rather than fabricated text offsets. AI and OCR are not part of this ingestion path.

## Dependency, contribution and release gates

CI runs in two tiers. The **fast tier** (`fast (amd64)`) runs on every pull request when it is opened, reopened or receives new commits: one native amd64 job running Ruff, Ruff format, strict mypy, the backend pytest suite against disposable PostgreSQL through `.github/backend_gate.py`, and the web type check, lint, tests and build. The **full tier** (the `gates` amd64 and arm64 matrix) runs on every push to `main`, on manual dispatch, and on a pull request labelled `full-ci`: it adds the arm64 leg, the shipped image build, pnpm audit, source and Python vulnerability gates, dependency inventory and SBOMs, the Trivy image and secret scans, and the disposable runtime and browser proof. Adding `full-ci` starts the full tier immediately; while the label stays on, each new push runs both tiers. Apply it once a pull request is otherwise ready, wait for green, then remove it. The `contribution` check is a separate workflow (`.github/workflows/contribution.yaml`) that runs on every pull request event, including description edits and labels; description edits never start the gate workflow, so they cannot replace current gate results with skipped ones. Labels other than `full-ci` start the gate workflow with both tiers skipped and never cancel a running gate; because the pull request page then shows those skipped rows as the latest, push again or re-add `full-ci` to restore visible results. A new push cancels the stale run for the same ref.

CI is configured for frozen backend/frontend gates on native Linux amd64 and arm64 runners, actual container/browser/recovery proof, source/secret checks, pinned pip-audit and pnpm audit, and pinned Trivy built-image vulnerability/secret/SBOM collection **without a mounted Docker socket**.
