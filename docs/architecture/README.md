# M0 architecture

Offerloom's current implementation is an architecture proof, not the planned M1 product. Its public runtime inputs are tracked source, locks, reviewed migrations and synthetic fixtures; ignored `.docs/` material is neither a build input nor an operational prerequisite.

## Components and persistence

- Python **3.12.15**, FastAPI/Pydantic, synchronous SQLAlchemy Core connections, psycopg using **system libpq**, Alembic and PostgreSQL **18.6**. No Redis or external broker.
- React/TypeScript/Vite, built with Node **22.23.4** and pnpm **10.33.3**. uv **0.13.0** installs the Python lock with frozen resolution; the image uses a non-editable production install. API serves the compiled UI from the same origin.
- An installation maintenance lock precedes workflow/resource locks. Version preconditions and owner/route/body/precondition idempotency fingerprints protect commands. Database-time leases, monotonic fences and guarded publication protect durable tasks; outbox receipts deduplicate local metadata consumption.
- Immutable profile/evidence/document revisions retain grounded claim references. Review binds an exact revision and content hash. A PDF artifact is served only after owner authorization, not as a public blob directory.
- PostgreSQL state, content-addressed blobs, renderer spool and encryption keys are separate persistence boundaries. The migrator's secret is not mounted in API/worker containers. Runtime owns no DDL objects; migration 004 controls table/function privileges, including the append-only audit restriction.

The implemented HTTP subset includes `/api/v1/auth/challenge`, `/bootstrap`, `/session`, `/session/password`, `/profile`, profile/claim/evidence history, `/imports`, `/postings`, `/sources`, `/workflows`, `/documents` and owner-authorized artifacts. Benchmark-only routes explicitly accept SYN-CORE and deterministic failure scenarios; production mode returns 404. Password policy is **15–128 characters**. Implemented OpenAPI comes from the actual application, not an unimplemented future contract; the [development guide](../development/README.md) distinguishes each deployed aggregate's version precondition.

## ADR-0002 — Sealed renderer deployment, revision 1

**Status:** M0 implementation decision; per-target runtime qualification is still required. **Date:** 2026-10-24.

**Context.** A renderer inside a credential-bearing worker must not inherit its filesystem, database or network access. The initial unprivileged `unshare --user --map-root-user --net` experiment was denied by the available Docker security boundary. Granting broad privileges, mounting the Docker socket or silently processing PDF inputs in the worker would break the required isolation.

**Decision.** Use a dedicated renderer service built from the same immutable application image. It runs UID/GID 10001, a read-only root, all capabilities dropped, no-new-privileges, bounded tmpfs/CPU/memory limits, effective container `pids.max=32` and `network_mode: none`. Its only persistent mount is `/spool`; it has no DB, blob, bootstrap or keyring mount/environment. The API/worker serialize validated typed document data; renderer-owned trusted templates and packaged fonts produce a bounded PDF; the worker verifies output and publishes the blob through its guarded transaction. Per-job subprocess CPU/address-space/file/descriptor/core limits and supervisor kill/reap deadlines are additional controls, not substitutes for the container boundary. `RLIMIT_NPROC` is deliberately not applied: Linux counts it across the shared service UID in other containers, which caused actual GLib thread-creation failures across simultaneous deployments. The cgroup is the per-container PID/thread ceiling. Arbitrary HTML/CSS/templates/URLs are not accepted.

**Consequences.** The renderer can read public code/libraries/fonts in its own image and shared spool content, not worker-private mounts. Spool cleanup, bounded output and failure handling remain part of the renderer protocol. A compromised renderer does not gain a network interface or Docker control socket. API/worker remain on internal-only networks; OL-007 adds a separately contained fixed-route source relay, described below, without changing renderer/parser isolation. Root is used only by the sealed, no-network, one-shot volume preparation helper, with the narrow `CHOWN` and `DAC_OVERRIDE` capabilities, to convert host-0600 secrets into distinct UID-owned 0400 volumes. Steady-state services are nonroot with no added capabilities.

**Qualification.** Inspect actual mount/cgroup/UID/capability state, demonstrate direct filesystem and network canaries from the renderer (bypassing its fetcher), and exercise real typed PDF rendering. The disposable probe implements these checks. Do not call an unsupported namespace configuration secure merely because a unit test or `network: internal` declaration is green.

## Loopback ingress boundary

API, migrator and PostgreSQL attach only to the internal `private` network; the worker also joins the internal `sources` network described below. None publishes host ports or receives a general external network route. A separate credential-free `ingress` service joins both `private` and a normal `ingress` bridge and publishes only `127.0.0.1:${OFFERLOOM_PORT:-8000}`. This avoids relying on host publication from an internal-only network, which did not work on the observed Docker Desktop engine. It forwards unchanged TCP bytes only to the fixed `api:8000` destination, preserving HTTP Host, Origin and CSRF behavior. It is not an HTTP proxy, does not implement CONNECT and accepts no destination from clients. The CI override uses a separate `db-access` relay fixed to `db:5432`, published only on `127.0.0.1:15432`; PostgreSQL remains private.

Both relays use the application image and Python standard library, run nonroot with a read-only root, all capabilities dropped and no-new-privileges, and have no mounts or application secret environment. Each is bounded to 128 MiB, 32 PIDs, half a CPU, 64 concurrent connections, a 64 KiB stream buffer/read chunk, a five-second upstream connection timeout, 60-second read/drain timeouts and a five-minute total connection lifetime. Asyncio stream drain provides backpressure; shutdown cancels active connections and closes sockets. The ingress container itself has a normal network route and is not an egress firewall; it carries no database credentials, keys, blob data or spool mounts. The restored API's actual outbound-socket refusal remains a separate probe requirement, alongside inspection of its internal-only network.

## OL-007 — Reviewed source transport boundary

The worker reaches `source-egress:8766` only over the internal `sources` network. The relay joins that network and a separate outbound bridge, not `private`; it has no database credentials, keyring, blobs, parser/render spools, persistent mounts or published host port. It uses the same immutable application image, nonroot read-only root, dropped capabilities and no-new-privileges, bounded to 256 MiB, 32 PIDs and half a CPU. Starting the relay does not load application settings or secrets. Its outage cannot prevent manual posting or unrelated durable work.

This is a fixed-route HTTP transport, not an arbitrary proxy or a new domain service. It constructs only the official HTTPS Greenhouse configured-board list GET from an ASCII-validated token. All resolved addresses must be public; connections use a vetted address with verified TLS host identity and checked peer before HTTP request bytes. Redirects, user URLs, submission methods, ambient proxy/authorization/cookies, unsupported encoding, malformed or incomplete lists and over-limit data fail closed. Original HTML becomes inert bounded text, never executable markup. Display-only reference URLs are never recursively fetched or claimed DNS-verified.

Source review, enablement, per-board scheduling, unknown provider quota, durable retry/cancellation/fencing and atomic provenance remain worker/database responsibilities. The relay cannot commit postings. Upstream Retry-After is a minimum wait and cannot be clamped downward; failure, disablement or missing posts never erase retained observations. The documented list endpoint returns all published posts, not a guaranteed paginated search API. Local acceptance uses an explicitly substituted test-only real TLS fixture; production startup cannot select that fixture from environment or API input. Technical endpoint availability does not clear board-specific collection rights.

## Images and native obligations

[Image metadata](../../deploy/images.json) records inspected official multi-platform index and amd64/arm64 manifest digests. Dockerfile assertions check the intended Python and Node versions during build. The PostgreSQL 18 image mounts **`/var/lib/postgresql`**, with `PGDATA=/var/lib/postgresql/18/docker`, matching its pinned official Dockerfile. Mounting the older `/var/lib/postgresql/data` convention is not used.

The application runtime uses official Python 3.12.15 on Alpine 3.24, supported through June 2028 for its main repository. It installs libpq, Pango/PangoFT2, HarfBuzz subset, JPEG/OpenJPEG, libffi, fontconfig, CA certificates and DejaVu fonts. `libpq-dev` supplies the unversioned linker name and binutils supplies `ld` for CPython's normal `ctypes.util.find_library("pq")` discovery; no compiler, discovery shim, vendored Psycopg binary or new Python build backend is introduced. This retains the existing frozen Python dependency graph. The initial Alpine probe without these discovery dependencies failed Psycopg import; the completed boundary passed both libpq import and the real sealed renderer under unchanged limits.

The build records installed APK package versions in `/usr/share/offerloom/native-packages.txt` and discovered fonts in `fonts.txt`. The exported-image collector preserves the actual APK installed database, package ownership, declarations, dependency/provider evidence and hashes of installed native/font/dictionary bytes. APK license declarations are not concluded SPDX licenses or proof that license texts, corresponding source, notices or relink obligations are fulfilled. Missing evidence stays explicitly review-blocked. Packages resolve from signed Alpine repositories at build time, not from the Python lock or pinned base digest; review the resulting image digest, inventory and vulnerability report because rebuilds can differ. Third-party fonts/native libraries retain their own licenses and are not relicensed under Offerloom's license choice.

## Unsupported and unqualified targets

Only Linux container arm64 and amd64 are intended M0 targets. macOS/Windows native application processes, remote-origin HTTP, arbitrary reverse proxies, rootless runtimes with incompatible volume ownership, unsupported Compose versions, and other CPU architectures are not qualified by this implementation. Docker Desktop may run a Linux guest; an amd64 image on an arm64 engine is **emulated**, not native. Before the Alpine migration, a Rosetta renderer diagnostic failed allocation with `rosetta error: mmap_anonymous_rw mmap failed` under the required 512 MiB process address-space ceiling; a throwaway diagnostic omitting only that ceiling succeeded with the 512 MiB container cap. Neither historical diagnostic qualifies the replacement image, and production containment was not weakened. Native amd64 qualification remains blocked on an available native target; its successful image build/security scan is not runtime qualification. A manifest entry is availability evidence only. Record actual application proof receipts for each target and distinguish native/emulated execution. No M1 readiness, production SLO, model quality, encrypted backup product or public-distribution clearance follows from M0.
